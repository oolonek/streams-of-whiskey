# Lightweight dashboard on GitHub Pages: hosting and data format

## Recommendation

Publish a **static, curated JSON snapshot exported by the Rust CLI** alongside HTML/CSS/JavaScript, not the crawler's live SQLite cache. This is the simpler path for a read-only table with sorting, filtering, and links: Pages serves static assets, while shipping SQLite requires an additional WASM runtime, browser database import/query code, and a compatible database snapshot. Keep the snapshot small by exporting only displayed fields; split it into files if initial download/parsing becomes noticeable. This is an architectural recommendation, not a measured browser performance result. [GitHub Pages overview](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages); [SQLite WASM loading guide](https://sqlite.org/wasm/doc/trunk/demo-123.md); [SQLite import cookbook](https://sqlite.org/wasm/doc/trunk/cookbook.md).

## Pages fit and deployment

- Pages hosts **static HTML, CSS, and JavaScript**, not the running Rust crawler or a server-side SQL endpoint. Project-site URLs default to `https://<owner>.github.io/<repository>/`; use site-relative asset paths that account for that prefix. A source branch can publish its root or `/docs`; if generating assets from Rust in CI, a custom Actions workflow can build the static directory and publish it with `actions/upload-pages-artifact` and `actions/deploy-pages`. [Pages overview](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages); [publishing sources and workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).
- The published site must be at most **1 GB**, source repositories have a **recommended** 1 GB limit, deployments time out after **10 minutes**, and the soft bandwidth limit is **100 GB/month** (plus a soft build-frequency limit of ten/hour, except custom Actions builds). Budget both the published bytes and per-visitor data transfers: approximately `snapshot bytes × visits`, before other assets and caching. [Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
- A Pages site is **public even when the source repository is private** (where private-repo Pages is available). Publish only reviewed public fields, never `HF_TOKEN`, private/gated results, or the raw local cache by accident. [Publishing-source warning](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## Data and optional SQLite WASM

- The repository already emits crawl `--json` JSONL, stores a 24-hour SQLite probe cache in ignored `.streams-of-whiskey.sqlite3`, and exports inspection results as a TSV with a row per **found** dataset, status (`complete`, `partial`, `ambiguous`, `error`), revision-pinned links and counts. A dashboard export should preserve scope/status and snapshot time rather than treating absent rows or `inconclusive` as negatives. [README](README.md); [cache schema](src/cache.rs); [.gitignore](.gitignore). At research time the local TSV was about **24 KB**, versus **3.5 MB** for the SQLite cache; these are only local artifact sizes, not a forecast for future crawls or JSON payloads.
- Browser SQLite is feasible **without a backend**: SQLite supplies `sqlite3.js` plus `sqlite3.wasm` and recommends a Worker for potentially long queries. The official recipe fetches an entire database into an `ArrayBuffer` and deserializes it into an in-memory database; browser/device limits determine viable sizes. The recipe warns that **WAL-mode databases cannot be imported this way**. The crawler explicitly enables SQLite WAL, so publishing the active `.sqlite3` file as-is is not a valid export plan: produce a consistent non-WAL snapshot first if choosing SQLite. [WASM guide](https://sqlite.org/wasm/doc/trunk/demo-123.md); [import cookbook](https://sqlite.org/wasm/doc/trunk/cookbook.md); [cache initialization](src/cache.rs).
- Persistent browser storage is unnecessary for a downloadable read-only snapshot. If considered later, SQLite's ordinary OPFS VFS runs in a Worker and requires COOP/COEP response headers for `SharedArrayBuffer`; SQLite identifies `opfs-sahpool` for hosts unable to set those headers. The `localStorage` VFS is typically limited to ~5 MB (less effective usable data), so it is a poor fit for a growing crawler cache. [SQLite persistence options](https://sqlite.org/wasm/doc/trunk/persistence.md). None of these browser-local stores turns Pages into a shared writable database.

**Decision point:** Use JSON while the displayed dataset is comfortably small and queries are simple. Reconsider a *separately generated*, consistent SQLite snapshot with WASM only if actual snapshot size or query complexity justifies the added load, format, and deployment constraints. [SQLite import cookbook](https://sqlite.org/wasm/doc/trunk/cookbook.md); [Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits).
